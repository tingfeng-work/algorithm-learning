# 华为 2026 年 4 月开发岗笔试真题复盘

## 一、训练概况

这两天完成了华为 2026 年 4 月开发岗的一套笔试真题，共包含三道题：

1. 版本号排序：字符串解析与自定义排序；
2. 魔导传输网：图论与最短路径；
3. 素材采购方案数：完全背包方案计数。

整体来看，三道题的算法难度不算高，主要考察能否正确理解业务规则、完成问题建模，并熟练运用基础算法。

## 二、第一题：版本号排序

### 1. 核心知识点

* 对复杂对象进行建模；
* 字符串分割与解析；
* `ArrayList.sort()`；
* `Comparator` 自定义排序；
* 匿名内部类。

### 2. 版本号建模

这道题首先让我认识到：当一个字符串包含多个具有不同含义的部分时，不应该直接在排序过程中反复处理原始字符串，而应该先将其解析成结构化对象。

为版本号建立了 `Version` 类：

```java
static class Version {
    String original;
    int[] mainParts;
    Integer beta;
}
```

各字段含义如下：

* `original`：保存原始版本号，用于排序后原样输出；
* `mainParts`：保存主版本号的各个数字部分；
* `beta`：保存测试版本编号，正式版使用 `null` 表示。

例如：

```text
1.0.2 beta3
```

解析后得到：

```text
original  = "1.0.2 beta3"
mainParts = [1, 0, 2]
beta      = 3
```

### 3. 输入解析

由于测试版版本号包含空格，不能使用只读取单个 Token 的 `next()`，而应该使用 `readLine()` 读取完整的一行。

解析分为两步：

1. 按空格分离主版本号和 `beta`；
2. 按 `.` 分割主版本号。

为了兼容多个空格，可以使用：

```java
line.trim().split("\\s+");
```

### 4. 自定义排序

使用 `ArrayList.sort()`，通过匿名内部类实现 `Comparator<Version>`。

比较顺序为：

1. 从左到右比较主版本号各部分；
2. 公共部分相同时，比较主版本号长度；
3. 主版本号完全相同时，测试版排在正式版之前；
4. 两者都是测试版时，比较 `beta` 编号。

这道题让我掌握了处理复杂排序问题的一般步骤：

```text
建立数据模型
→ 解析原始输入
→ 明确字段优先级
→ 实现自定义比较器
→ 输出原始数据
```

匿名内部类并不是因为排序算法本身复杂，而是因为需要为当前题目临时定义一套专用的比较规则。

## 三、第二题：魔导传输网

### 1. 核心知识点

* 图的基本表示；
* 深度优先搜索 DFS；
* 广度优先搜索 BFS；
* Dijkstra 单源最短路径；
* Floyd 多源最短路径；
* 邻接矩阵与邻接表；
* 优先队列与小顶堆。

图论的基本概念在本科阶段已经学习过，这次主要进行了复习，并进一步掌握了常见最短路径算法的适用场景。

### 2. DFS 与 BFS

DFS 和 BFS 是图遍历的基础。

* DFS 沿一条路径不断深入，适合连通性判断、回溯搜索和路径枚举；
* BFS 按层扩展，在无权图中可以求最短路径。

虽然本题最终使用的是最短路径算法，但 DFS、BFS 是进一步学习图论算法的重要基础。

### 3. Dijkstra 算法

Dijkstra 用于求解边权非负情况下的单源最短路径。

其核心思想是：

> 每次从尚未确定最短距离的节点中，选出当前距离起点最近的节点，并确定其最短距离，再通过该节点更新其他节点的距离。

Dijkstra 有两种常见实现。

#### 朴素 Dijkstra

* 通常使用邻接矩阵；
* 每次遍历所有节点寻找距离最小的未确定节点；
* 时间复杂度为 (O(N^2))；
* 更适合节点数较少或边较多的稠密图。

#### 堆优化 Dijkstra

* 通常使用邻接表；
* 使用优先队列维护当前距离最小的节点；
* 时间复杂度约为 (O((N+M)\log N))；
* 更适合边数较少的稀疏图。

### 4. Floyd 算法

Floyd 用于计算任意两个节点之间的最短路径，即多源最短路径。

三维动态规划状态可以定义为：

[
f[k][i][j]
]

表示只允许使用前 (k) 个节点作为中间节点时，从节点 (i) 到节点 (j) 的最短距离。

状态转移为：

[
f[k][i][j]
==========

\min\left(
f[k-1][i][j],
f[k-1][i][k]+f[k-1][k][j]
\right)
]

空间压缩后使用二维数组：

[
dp[i][j]
]

表示当前阶段节点 (i) 到节点 (j) 的最短距离：

```java
for (int k = 0; k < n; k++) {
    for (int i = 0; i < n; i++) {
        for (int j = 0; j < n; j++) {
            dp[i][j] = Math.min(
                dp[i][j],
                dp[i][k] + dp[k][j]
            );
        }
    }
}
```

其中：

* `k` 枚举允许经过的中间节点；
* `i` 枚举起点；
* `j` 枚举终点。

因此，`k` 必须放在最外层。

Floyd 的时间复杂度为：

[
O(N^3)
]

空间复杂度为：

[
O(N^2)
]

适合节点数较小、查询次数较多的场景。

### 5. 本题实现中的易错点

* 题目给出的是无向图，需要同时保存 `dis[x][y]` 和 `dis[y][x]`；
* 两个节点之间可能存在重边，应保存最小边权；
* 不可达节点之间的距离需要初始化为无穷大；
* 计算新距离前要避免无穷大参与加法；
* `FastScanner` 应在当前行没有 Token 时读取下一行：

```java
while (st == null || !st.hasMoreTokens())
```

## 四、第三题：素材采购方案数

### 1. 核心知识点

* 完全背包；
* 方案计数；
* 问题转化；
* 一维动态规划；
* 边界条件处理。

### 2. 问题转化

题目要求每种素材至少购买一个，因此可以先强制购买每种素材一个。

假设总预算为 `budget`，各素材价格为 `price[i]`，则新的目标金额为：

[
target=budget-\sum price[i]
]

完成这一步之后，问题就转化为：

> 每种素材还可以额外购买任意多个，求恰好使用完剩余预算 `target` 的方案数。

这就是完全背包方案计数问题。

### 3. 状态定义

```java
dp[j]
```

表示使用已经遍历过的素材，恰好凑出额外预算 `j` 的方案数。

初始化：

```java
dp[0] = 1;
```

含义是：

> 凑出额外金额 0 有一种方案，即不再额外购买任何素材。

### 4. 状态转移

```java
for (int price : prices) {
    for (int j = price; j <= target; j++) {
        dp[j] += dp[j - price];
    }
}
```

状态转移表示：

* 原有的 `dp[j]`：不额外购买当前素材；
* `dp[j - price]`：至少再购买一个当前素材。

金额必须从小到大遍历，这样当前素材才能在同一轮中被重复使用，符合完全背包的要求。

### 5. 相同价格的素材

即使两种素材价格相同，它们仍然属于不同种类。

因此不能提前对价格去重，而应该让每一种素材分别执行一轮完全背包转移。这样才能正确区分不同素材之间的购买数量分配。

### 6. 边界条件

如果购买每种素材一个后：

* `target < 0`：预算不足，方案数为 0；
* `target == 0`：恰好只购买每种素材一个，方案数为 1；
* `target > 0`：进入完全背包计算。

实现时只需要特殊处理 `target < 0`：

```java
if (target < 0) {
    System.out.println(0);
    return;
}
```

当 `target == 0` 时，`dp[0] = 1` 可以自然得到正确答案。

## 五、三道题的共同收获

这三道题虽然分别涉及字符串、图论和动态规划，但解题过程具有相同结构：

```text
理解业务规则
→ 抽象数据和状态
→ 识别基础算法模型
→ 处理输入与边界
→ 编写并验证代码
```

第一题的重点是对版本号进行结构化建模；第二题的重点是根据图的规模和查询方式选择最短路径算法；第三题的重点是通过“每种素材先购买一个”将业务限制转化为标准完全背包。

## 六、心得体会

整体来说，这三道题并不属于特别困难的算法题，使用的都是较为基础和经典的算法。真正重要的是能否从业务描述中提取约束，完成正确建模，并迅速匹配到合适的算法。

这次真题训练对我最大的帮助，是弥补了此前刷题过程中图论内容相对不足的问题。我系统复习了 DFS、BFS、Dijkstra 和 Floyd，并理解了它们各自的适用场景。

同时，这次练习也暴露出一个需要继续改进的问题：算法主体即使正确，输入读取、无向边、重边、提前返回等实现细节仍然可能导致整道题无法通过。因此，今后完成代码后需要固定检查：

1. 输入格式是否被正确解析；
2. 有向图和无向图是否区分正确；
3. 是否存在重边、不可达和溢出问题；
4. 边界分支输出后是否需要 `return`；
5. 数据范围是否支持当前算法复杂度；
6. 输出格式是否严格符合要求。

通过这次训练，我不仅补充了图论算法，也进一步认识到：笔试能否通过，取决于“正确建模、算法选择、实现细节和边界检查”四个环节，而不只是能否写出核心状态转移。
